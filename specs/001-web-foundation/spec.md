# 特性规格：网页客户端骨架与用户认证

**特性分支**：`001-web-foundation`

**创建日期**：2026-09-23

**状态**：草稿

**输入**：用户描述："搭建网页客户端的整体框架：前后端分离工程骨架、本地一键联调、健康检查，并从一开始按多用户模式设计，交付真实的用户注册/登录（用户名+密码、令牌登录、无邮箱验证）与网页端登录门禁。不做论文提交、Key 管理、阅读页等后续功能。"

### 用户故事 1 - 一键本地启动并看到健康状态（优先级：P1）

作为开发者/运维者，我用文档中写明的命令在自己的机器上启动后端服务和
网页前端，打开浏览器就能立刻看到两层服务已连通且状态健康，从而让后续每个
功能都有可集成的基础。

**为什么是这个优先级**：没有可运行、已连通的骨架，后续任何能力都无处
集成；它同时验证了宪法要求的本地离线验收路径。

**独立测试**：在一份干净的代码检出上，仅按安装说明启动两个服务，打开
浏览器，看到前端落地页以及"后端可达且健康"的状态指示，全程不发起任何
外部网络调用。

**验收场景**：

1. **假定**项目已检出且依赖已安装，**当**运维者按文档命令先后启动后端和
   前端，**那么**浏览器展示应用落地页，且页面显示后端服务可达、状态健康。
2. **假定**两个服务正在运行，**当**后端被停止，**那么**前端明确提示服务
   不可用，而不是静默失败。
3. **假定**机器处于断网状态，**当**在本地启动系统，**那么**启动与健康
   检查依然成功（不联系任何第三方服务）。

### 用户故事 2 - 注册新账户（优先级：P1）

作为首次访问者，我在网页上用用户名和密码创建账户，以便我后续的工作
（API Key、转写任务）归属于我本人，并与其他用户隔离。

**为什么是这个优先级**：用户身份是后续所有多用户功能的数据归属根基；
没有真实身份，就无法安全地存放每用户私有数据。

**独立测试**：访问者打开注册页，提交合法用户名和密码，得到账户创建
成功的确认，并能立即登录。

**验收场景**：

1. **假定**用户名尚未被注册且密码符合规则，**当**访问者提交注册表单，
   **那么**账户被创建，访问者被引导去登录。
2. **假定**用户名已被注册，**当**访问者提交表单，**那么**注册被拒绝并
   明确提示用户名已占用，且不会产生重复账户。
3. **假定**用户名或密码违反输入规则（长度、允许字符、空字段），**当**
   访问者提交，**那么**表单指出具体问题，且不创建任何账户。
4. **假定**注册成功，**当**检查落库的账户数据，**那么**密码绝不以明文
   形式存在，也不出现在任何日志中。

---

### 用户故事 3 - 登录并向系统证明身份（优先级：P1）

作为已注册用户，我用用户名和密码登录，获得一个安全的登录令牌，并用它
访问一个受保护的"已登录区域"占位页，从而让系统能可靠地区分我、其他用户
以及匿名访问者。

**为什么是这个优先级**：认证会话是宪法中多租户隔离原则的执行点，后续
所有受保护功能都依赖它。

**独立测试**：已注册用户用正确凭据登录，进入显示本人身份的受保护页；
错误凭据和被篡改的令牌一律被拒绝。

**验收场景**：

1. **假定**存在一个已注册账户，**当**用户提交正确的用户名和密码，
   **那么**用户获得登录令牌，并能打开显示其用户名的受保护页。
2. **假定**存在一个已注册账户，**当**用户提交错误密码，**那么**登录被
   拒绝，返回笼统的"用户名或密码无效"提示，且不签发令牌。
3. **假定**匿名请求不带令牌，或令牌无效/过期/伪造，**当**它访问任何
   受保护能力，**那么**访问被拒绝并返回未授权响应。
4. **假定**服务被重启，**当**此前已注册的用户再次尝试登录，**那么**
   账户依然存在且登录成功（账户可跨重启保留）。

---

### 用户故事 4 - 网页路由门禁与退出登录（优先级：P2）

作为已登录用户，在登录前我无法进入内部页面；登录后我应回到原本想去的
页面；我还能退出登录，使我的会话在共用机器上彻底结束。

**为什么是这个优先级**：统一的前端门禁可以避免内部页面闪现或被 URL
直接绕过；退出登录是多用户产品基本的会话卫生要求。

**独立测试**：匿名用户直接输入内部页 URL 被跳转到登录页，认证后回到
该页；退出后无法再访问受保护页面。

**验收场景**：

1. **假定**用户未登录，**当**直接访问任何内部页面 URL，**那么**被
   重定向到登录页。
2. **假定**匿名用户是从某个具体内部页被重定向来的，**当**登录成功，
   **那么**被送回最初请求的那个页面。
3. **假定**用户已登录，**当**选择退出登录，**那么**其令牌被丢弃，
   受保护区域不可再访问，用户回到登录/落地页。
4. **假定**会话期间令牌过期，**当**用户下次执行受保护操作，**那么**
   被干净地引导重新登录。

---

### 用户故事 5 - 统一应用框架与视觉基线（优先级：P2）

作为已登录用户，我在任何内部页面都看到同一套布局与交互风格：顶部栏
显示我的身份和退出入口、内容区承载具体功能、导航区域为后续功能预留
位置，从而让后续每个新页面都像同一个产品的一部分，而不是拼凑出来的。

**为什么是这个优先级**：它不直接产生业务价值，但决定了后续两个特性的
页面是"填入框架"还是"各写一套"；在第一个特性确立基线成本最低，可避免
三个特性样式与请求逻辑各自返工。

**独立测试**：登录后在受保护占位页与后续新增的空白页面间切换，确认
布局连续、风格统一；断开登录状态后，任意页面操作都被统一引导回登录。

**验收场景**：

1. **假定**用户已登录，**当**打开任意内部页面，**那么**页面呈现统一
   布局框架：顶部区域显示当前用户名与退出入口，主体区域承载页面内容，
   并存在为后续功能预留的导航位置。
2. **假定**用户在不同内部页面间切换，**当**观察表单、按钮、成功与失败
   提示的呈现方式，**那么**它们风格一致、反馈方式统一，没有明显的视觉
   跳变。
3. **假定**用户持有有效令牌，**当**前端与后端通信，**那么**身份凭证由
   统一的请求通道自动附带，业务页面无需各自处理。
4. **假定**用户令牌已失效，**当**在任意页面发起需要身份的操作，**那么**
   被统一引导至登录流程，而不是各页面表现出互不相同的错误行为。

---

### 边界情况

- 两个访问者几乎同时注册同一个用户名：恰有一个成功，另一个收到重复
  提示。
- 用户名不存在与密码错误两种登录失败返回完全相同的笼统提示，避免泄露
  哪些用户名已注册。
- 仅含空白字符、超长的用户名，以及过短的密码，在入库前即被拒绝。
- 用其他密钥签名的令牌、结构损坏的令牌，与缺失令牌得到同样的拒绝处理。
- 系统时钟变化或服务重启不得使已存储账户失效；只有令牌自身过期才结束
  会话。
- 在无互联网的机器上注册/登录必须可用，不联系任何外部身份或验证服务。

## 需求 *（必填）*

### 功能需求

- **FR-001**：系统必须提供浏览器可访问的前端和独立的后端服务，二者能在
  一台本地机器上按文档化的启动命令同时运行。
- **FR-002**：系统必须暴露一个无需认证的健康指示能力，供前端展示，至少
  覆盖后端是否可达。
- **FR-003**：系统必须持久化已注册账户，使账户在服务重启后依然有效。
- **FR-004**：访问者必须能用唯一用户名和密码注册；用户名必须唯一并满足
  文档化的长度与字符规则，密码必须满足文档化的最低强度。
- **FR-005**：系统只能以加盐、不可逆哈希的形式存储密码；严禁存储明文
  密码或将其写入日志。
- **FR-006**：已注册用户必须能用用户名和密码登录，并获得一个有时限的
  登录令牌，用于在后续请求中证明身份。
- **FR-007**：系统必须提供至少一个受保护能力，只有持有效令牌才能访问，
  且该能力回报当前认证用户本人的身份。
- **FR-008**：令牌缺失、格式错误、过期、伪造的请求，以及凭据无效的请求，
  必须被拒绝并返回恰当的未授权响应；登录失败必须返回笼统提示，不区分
  "用户名不存在"与"密码错误"。
- **FR-009**：每个受保护的服务端交互必须通过单一的集中式认证检查，从
  令牌解析身份；禁止在各端点零散地临时鉴权。
- **FR-010**：前端必须用单一的集中式路由门禁保护所有内部页面：匿名访问
  跳转登录，登录后回到最初请求的页面。
- **FR-011**：已登录用户必须能退出登录；退出后其令牌不再授予访问权，
  内部页面不可再达。
- **FR-012**：注册与登录必须完全离线可用，不依赖任何外部服务，符合宪法
  的离线可验收原则。
- **FR-013**：账户创建、密码存储与受保护访问必须有自动化测试覆盖，测试
  可在无第三方服务、无网络的条件下运行。
- **FR-014**：现有 core 转写逻辑必须保持零改动；本特性不向 `core/` 引入
  任何行为变化，也不新增必填参数。
- **FR-015**：前端必须提供统一的已登录区域布局框架：顶部区域展示当前
  用户身份与退出入口，主体区域承载各功能页面，并为后续功能预留导航
  位置；后续特性的页面必须在该框架内呈现，无需另建布局。
- **FR-016**：前端必须建立统一的视觉与交互基线：一致的组件风格、主题与
  操作反馈（成功/失败/加载提示）方式；并须具备展示富文本与数学公式的
  基础渲染能力，供后续阅读器特性直接使用（本特性不交付阅读器页面）。
- **FR-017**：前端与后端的所有通信必须经过单一统一请求通道：自动附带
  登录令牌、统一处理未授权响应（回到登录流程）与网络不可用提示；业务
  页面不得各自实现凭证附带或错误跳转逻辑。

### 关键实体 *（涉及数据时必填）*

- **用户（User）**：可登录的人。关键属性：唯一用户名、不可逆哈希密码、
  账户创建时间。用户是后续功能挂载 API Key 与转写任务的归属根基。
- **登录令牌（Login Token）**：登录成功后签发的有时限、防篡改凭证，在
  后续请求中代表用户身份；它会自行过期，或在用户退出登录时失效。

## 成功标准 *（必填）*

### 可测量结果

- **SC-001**：新运维者仅按项目文档，能在干净机器上 10 分钟内装好依赖、
  启动前后端，并看到健康状态。
- **SC-002**：首次访问者能在 2 分钟内完成注册、登录并看到认证后的占位
  页面。
- **SC-003**：未持有效令牌访问受保护页面或能力的尝试，100% 被拦截
  （覆盖直接输入 URL、页面刷新、直接发服务端请求三种路径）。
- **SC-004**：错误凭据的登录尝试 100% 被拒绝；从落库数据或日志中永远
  无法还原任何账户的明文密码。
- **SC-005**：已注册账户在服务重启后 100% 保留；在断网机器上，注册—
  登录—受保护访问全流程可用。
- **SC-006**：受测者在登录后各页面间切换时，100% 看到连续一致的布局与
  交互风格，且令牌失效后任意操作都被统一引导至登录（无页面各自报错的
  情况）。

## 假设

- 认证采用"用户名 + 密码 + 有时限令牌"，v0 刻意简化：不做邮箱验证、
  密码找回、验证码、失败锁定策略，这些留给后续 spec。
- 系统从一开始按多用户设计（数据归属与访问校验），但本阶段不交付管理
  后台、用户管理界面或注册审批流。
- 本阶段部署目标是本地开发机；生产加固（HTTPS、规模化 Cookie 标志、
  密钥分发）不在范围内，但代码结构不得阻碍未来的多用户部署。
- 技术选型已由项目宪法固定（独立 API 服务、单页网页客户端、文件型关系
  数据库）；本规格只定义行为，实现细节归技术方案（plan）所有。
- 机器提供可写的本地存储以持久化账户数据；完成上述流程无需任何第三方
  账户或服务。
- 视觉基线仅指统一布局、主题、组件风格与反馈方式等"框架级一致性"，
  不包含配色定制、动画、品牌化等视觉精修（宪法已列为 v0 不做）。
