# 论文易读化 Web 客户端宪法

## 核心原则

### 原则一：core 业务逻辑冻结（不可协商）

`core/` 包的六模块流水线（ingest、mineru_client、normalize、planner、
rewrite、assemble）及其提示词资产（`core/prompts/`）不得因网页客户端的
需要而修改。Web 阶段唯一允许的变更是在 `transform_paper()` 上以增量方式
新增可选参数 `cancel_event`，默认值为 `None`，保证现有行为逐字节不变。
任何进一步的 core 改动必须单独提出、说明理由并作为独立 spec 获批后才能
实施。接口演进遵循"只增不改"：新参数必须带默认值；禁止删除或重新定义
已有字段。

### 原则二：继承 core 的架构边界

Web 层必须保留 core 既有原则：纯函数边界（副作用只留在 ingest /
MinerUClient / llm.chat）、所有配置依赖注入（不硬编码 key 或 URL）、
数据契约可 JSON 序列化。持久化、认证、HTTP、任务队列等关注点只存在于
Web 层，不得反向渗入 `core/`。Web 层只通过 core 的公共入口及可独立调用
的子模块来使用它。

### 原则三：多租户隔离（不可协商）

即使在本地运行，系统也从第一天起按多用户设计。每个任务、密钥、结果和
产物的查询都必须在服务边界对照已认证用户 id 做授权——任何端点都不得
接受或返回其他用户的任务 id 或文件路径。运行产物存放在
`runs/<user_id>/<task_id>/` 下，文件只能通过需要登录且校验归属的端点
提供，绝不通过裸文件系统路径暴露。

### 原则四：凭据与密钥安全

第三方 API Key 必须加密落库（Fernet；主密钥只能从环境变量
`WEB_MASTER_KEY` 读取），对外接口只回显掩码形式。密码必须使用
pbkdf2_sha256 哈希（全代码库共用唯一一份 CryptContext 配置）；严禁记录
明文密码和密钥、严禁将其提交到 git 或内嵌进前端代码。所有密钥只能来自
环境变量或每用户加密记录，绝不来自提交到仓库的配置文件。

### 原则五：长耗时任务不得占用请求路径

论文转写是耗时数分钟的同步 core 调用。HTTP 请求处理器不得阻塞在上面：
执行放在有界线程池中，通过 `anyio.to_thread` 桥接；进度只能经由 core
现有的 `progress_cb` 流出，写入任务状态并经 SSE 推送。执行器必须定义在
接口之后，使未来基于队列的实现（Celery/RQ）可以在不改动路由的前提下
替换进程内线程池。每用户并发限制为一个运行中任务；全局上限是配置项。
取消只能在阶段边界生效（MinerU 轮询循环、章节转写之间）；生成过程中
硬中断不在范围内。

### 原则六：契约先行，前后端分离

Pydantic 模式与 OpenAPI 文档是 FastAPI 与 Vue 单页应用之间的唯一契约。
前端不得 import core、不得访问文件系统、不得直接构造数据库查询；只能
通过有版本的 REST/SSE API 通信。认证在后端通过单一 `get_current_user`
依赖集中强制，在前端通过统一路由守卫（`requiresAuth` 元信息 +
`beforeEach`）集中强制；禁止散落的逐个调用鉴权判断。

### 原则七：默认离线可验收

假模式（`WEB_FAKE_MODE=1`，驱动 core 的 `fake=True`）必须保证注册、
提交、进度、阅读、下载的完整 Web 流程在零外部 API 调用、无已存密钥的
情况下可演示。每个特性必须可离线验收；core 的错误三分类
（InputError / ServiceError / ETError）必须映射为彼此区分的、面向用户的
失败提示。

## 阶段范围与技术约束

- **后端**：FastAPI + SQLAlchemy + SQLite，位于 `web/`。Python 3.11+。
- **前端**：Vue 3 + Vite + Pinia + Vue Router + Naive UI，位于 `webui/`。
- **实时进度**：本阶段只用 SSE（不用 WebSocket）。
- **后台执行**：进程内线程池；本阶段不用 Celery/Redis。
- **在范围内（v0）**：骨架与本地运行、真实认证（用户名+密码、JWT、无
  邮箱验证）、每用户加密 Key、链接/PDF 提交、带友好错误映射的任务执行、
  SSE 进度、历史、阶段边界取消、在线阅读器（7 章导航、KaTeX、
  `<details>`、图片）与 .md 下载。
- **明确不做**：管理后台、配额计费、邮箱验证、分享协作、Celery/Redis、
  公网部署/HTTPS 运维、视觉精修。

## 开发流程与质量门

- 工作按特性逐个推进，走 Spec Kit 闭环：
  constitution（仅一次）→ specify → clarify（需要时）→ plan → tasks →
  analyze → implement → converge，重复直到 converge 报告 **Converged**。
- 每个 spec 实现前手动运行 `/speckit-analyze`；实现后以
  `/speckit-converge` 作为人工验收门。
- 每个 spec 切成可独立测试的用户故事；特性只有在其验收场景于假模式下
  端到端通过时才算完成。
- 提示词资产改动（本阶段预期无）需用至少两篇论文回归；core 的后处理
  三件套（标题降级、死链修复、公式回填）必须保留。
- 本地验收方式：`uvicorn` 后端 + `npm run dev` 前端，由 Vite 代理 API。

## 治理规则

本宪法在 Web 客户端阶段优先于一切临时约定。所有 spec、plan 与代码评审
必须核对是否符合原则一至七；与某条原则冲突的提案须先修订本宪法。修订
采用语义化版本：删除/重定义原则为 MAJOR，新增原则或实质扩充指引为
MINOR，澄清性修改为 PATCH。每次修订必须附同步影响报告，说明版本变化、
受影响原则与迁移影响，并在依赖它的 spec 进入规划前获批。`docs/` 下已有
架构文档（architecture.md、services.md、data-model.md）仍是全局事实
来源；本宪法在其上治理 Web 阶段。
